# AIO Industrial Connector

Custom **Akri connectors for Azure IoT Operations (AIO)** that poll industrial devices and publish each asset dataset as a JSON message to the AIO MQTT broker or the broker state store. One codebase, one executable, **one protocol per instance**:

| Protocol | Mode | Endpoint type | Devices | Docs |
| --- | --- | --- | --- | --- |
| **Modbus TCP** | `modbus` | `Custom.ModbusTcp` | PLCs, energy meters, drives, TCP-to-RTU gateways | [docs/modbus](docs/modbus/README.md) |
| **Siemens S7** | `s7` | `Custom.SiemensS7` | S7-300 / 400 / 1200 / 1500 | [docs/s7](docs/s7/README.md) |

It is built on the [Azure IoT Operations .NET connector SDK](https://github.com/Azure/iot-operations-sdks) (`PollingTelemetryConnectorWorker`), [NModbus](https://github.com/NModbus/NModbus) and [S7netplus](https://github.com/S7NetPlus/s7netplus). It targets **.NET 10** (see [OPENPOINTS.md](OPENPOINTS.md)).

```text
 Modbus device ─┐                         ┌────────────────────────────┐
                ├─ protocol ─▶ connector pod ──MQTT──▶ AIO broker ──▶ data flows / cloud
 S7 PLC ────────┘   module     (one mode)  └────────────────────────────┘
                                     ▲
        Azure Device Registry: Device (endpoint) + Asset (datasets, data points)
```

## How the modes work

The same image code runs in whichever mode it is started in: `CONNECTOR_PROTOCOL=modbus|s7` (or `--protocol <name>`). The published images bake the mode in, so there are two images, two metadata artifacts and two connector templates that never interact:

| | Modbus | S7 |
| --- | --- | --- |
| Image | `aio-modbus-connector` | `aio-s7-connector` |
| Connector template (default name) | `modbus-tcp-connector` | `s7-connector` |
| Leader election lock | `aio-modbus-connector-leader` | `aio-s7-connector-leader` |

Everything protocol-independent — sampling loop, retry and partial-result policy, settings cascade, plan validation, request merging, JSON payload and schema, connection pooling, hosting — lives once in `src/Core`. A protocol only adds addresses, a data point model, a decoder and a client. Details and design patterns: [ARCHITECTURE.md](ARCHITECTURE.md).

## What both modes do

- Read-only polling with one timer per dataset; adjacent data points merged into as few requests as possible.
- One shared connection per device, reconnect on failure, per-request timeouts, one automatic retry on a fresh connection.
- Partial results: a request the device rejects publishes `null` for its points; the others are still published.
- The whole configuration is validated up front and every error is reported on the device status (visible in the portal).
- A **JSON Schema** per dataset is registered in the AIO schema registry; a `connector-metadata.json` per protocol gives the **operations experience** protocol-specific form fields.

Example payloads:

```json
{"temperature":25.53,"humidity":50.7,"cycleCounter":3,"running":true,"alarm":false,"flowRate":11.69,"pumpOn":true}
```

## Quick start (local, 1 minute)

```powershell
dotnet test --solution AIOIndustrialConnector.slnx
dotnet run --project src/Tools/IndustrialProbe -- --protocol modbus --device deploy/modbus/k8s/device.yaml --asset deploy/modbus/k8s/asset.yaml --simulator --count 3
dotnet run --project src/Tools/IndustrialProbe -- --protocol s7     --device deploy/s7/k8s/device.yaml     --asset deploy/s7/k8s/asset.yaml     --simulator --count 3
```

## Status

Version 0.2.0, preview. Built and tested locally (159 tests: Core 14, Modbus 72, S7 73; probe against both simulators; S7 container image built and checked). **Not yet run on a live AIO cluster, and the S7 mode not yet tried against a real PLC** — see [OPENPOINTS.md](OPENPOINTS.md).
